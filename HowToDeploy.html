🚀 How to Deploy Manually — TradeNet Admin Report

The exact commands deploy.bat / deploy.ps1 run for you, typed out one at a time — so you understand every step.

💡Why manual? There's a script (deploy.bat) that does all of this automatically — but this guide is for doing it by hand, step by step, so you learn exactly what "deploying" means: pulling code, building it, and carefully copying the new files onto the live server without breaking anything for users who are on the site right now.

✅ Before you start

🖥️You're on the Build Server (RDP session) with the repo already cloned there — this is the only machine wired up to reach the live server's folders.
🧰You have a PowerShell window open, in the repo's root folder.
💾Your code is committed and pushed to main on GitHub — you're about to pull and deploy that, not whatever is sitting unsaved on your laptop.
📋You know the two real target folders (backend + frontend) and the health-check URL for the environment you're deploying to. See Part C below — ask your lead if unsure.

🗺️ The big picture

Deploying by hand is really just two independent jobs, done back to back — the API (backend) and the website (frontend):

Get latest code
→
Build backend
→
Pause API briefly
→
Copy new backend files in
→
Un-pause API
Build frontend
→
Copy new website files in
→
Check it's alive
🩹What "pause the API" means You drop a file called app_offline.htm into the live API's folder. This is a special filename that IIS recognizes — it politely shuts down the running API and shows that page to users instead of an error while you copy files in. Deleting that file afterwards brings the API back to life. It's the standard, safe way to update a live IIS site without anyone seeing a crash.

⚙️ Part A — Deploy the Backend (API)

1

Get the latest code

cd "path\to\repo"
git pull --ff-only
⚠️If this fails It means there are local changes sitting in this repo folder that would get overwritten. Run git status and ask a senior dev before discarding anything — don't guess.
2

Build the backend

cd Backend
dotnet build API.csproj -c Release

This just compiles the code and checks for errors. It doesn't touch the server yet.

3

Publish it to a local folder

dotnet publish API.csproj -c Release -o ..\.deploy\backend-publish

This packages everything the API needs to run into .deploy\backend-publish — still just on this machine, nothing has gone to the live server yet.

4

Remove the settings files from that folder

cd ..\.deploy\backend-publish
Remove-Item appsettings.json -Force -ErrorAction SilentlyContinue
Remove-Item appsettings.*.json -Force -ErrorAction SilentlyContinue
🔐This step is not optional The live server's real appsettings.json holds the database password and secret keys. If you copy your local one over it, you can break the live database connection or leak secrets. Deleting it here means the copy step (next) simply won't touch whatever is already on the server.
5

Tell the live API to pause

New-Item -Path "BACKEND-TARGET-FOLDER\app_offline.htm" -ItemType File -Force
Start-Sleep -Seconds 5

Users now briefly see a "Deploying an update…" page instead of the live app. The short wait gives the running API time to fully shut down and release its files.

6

Copy the new backend files in

robocopy "..\.deploy\backend-publish" "BACKEND-TARGET-FOLDER" /E /XF appsettings.json appsettings.*.json app_offline.htm

/E copies all files and subfolders. /XF means "exclude these files" — so you never accidentally wipe out the server's real settings or the pause page you just created.

ℹ️Reading the result Robocopy prints an exit code. 0–7 = success (even "1" is normal, it just means files were copied). 8 or higher = something failed — see Troubleshooting.
7

Bring the API back online

Remove-Item "BACKEND-TARGET-FOLDER\app_offline.htm" -Force

The moment this file is gone, IIS lets the API start answering requests again — with your new code.

🖥️ Part B — Deploy the Frontend (website)

8

Point the build at the right API

cd ..\..\Frontend
$env:VITE_BASE_URL  = "https://THE-REAL-API-ADDRESS/api/"
$env:VITE_IMAGE_URL = "https://THE-REAL-API-ADDRESS/Image/"
$env:VITE_QR_URL    = "https://api.ecomreg.gov.mm/QR/"

The website bakes these addresses into itself when it's built — this is how it knows which API to talk to once it's live. Get the real API address from your lead (see below) — don't leave it as localhost.

9

Build the website

npm install --legacy-peer-deps
npm run build

This creates a Frontend\dist folder containing the finished, ready-to-publish website.

10

Copy the website files in

robocopy "dist" "FRONTEND-TARGET-FOLDER" /E /XF web.config

Same idea as the backend copy — /XF web.config protects the server's existing config file from being overwritten by your local one.

ℹ️No pause needed here Unlike the API, a website's static files can usually be swapped in directly without an "offline" step — visitors just get the new files on their next page load.

✅ Part C — Confirm it worked

11

Check the API is responding

curl "https://THE-REAL-HEALTH-URL/health"

You're looking for a quick, successful response (HTTP 200). If it hangs or errors, the API may still be starting up — wait a minute and try again before assuming it failed.

12

Check the website in a browser

Open the live site and hard-refresh: Ctrl+Shift+R. Confirm reports load real data, not just a blank page.

⚠️ Confirm the real target folders/URLs first

🎯Don't guess these values This guide uses placeholders like BACKEND-TARGET-FOLDER, FRONTEND-TARGET-FOLDER, THE-REAL-API-ADDRESS, and THE-REAL-HEALTH-URL on purpose. Server folder paths and addresses can change over time (for example, whenever an environment gets promoted from testing to live) — ask a senior dev for today's real values before your first manual deploy, and write them down somewhere for next time. Deploying to the wrong folder can mean your changes go live on the wrong environment, or don't show up at all.

🩺 If something goes wrong

❌git pull fails
→ Uncommitted changes are sitting in the repo folder on the Build Server. Run git status, ask a senior dev before discarding anything.
❌dotnet build or dotnet publish fails
→ Read the actual compiler error above the failure — it points at the file/line. Don't proceed to copying files if the build failed.
⏳Copy step (robocopy) can't overwrite API.dll
→ The old process hasn't fully released the file yet. Wait a few more seconds after dropping app_offline.htm, then retry the robocopy command alone (steps 5 already ran, no need to repeat them).
❌Robocopy exits with code 8 or higher
→ A real copy failure (permissions, disk, or a locked file). Copy the console output and ask a senior dev — don't re-run repeatedly.
🔄Everything copied fine but the site still looks old
→ Browser cache. Hard-refresh with Ctrl+Shift+R.
❌Forgot to delete app_offline.htm (step 7)
→ The site stays stuck on "Deploying an update…" forever. Go back and delete that file from the backend target folder.

📇 Quick reference — every command in order

Once you've done this a few times and understand each step, here's the full sequence together (still replace every red placeholder with the real values first):

# --- Backend ---
cd "path\to\repo"
git pull --ff-only
cd Backend
dotnet build API.csproj -c Release
dotnet publish API.csproj -c Release -o ..\.deploy\backend-publish
cd ..\.deploy\backend-publish
Remove-Item appsettings.json -Force -ErrorAction SilentlyContinue
Remove-Item appsettings.*.json -Force -ErrorAction SilentlyContinue
New-Item -Path "BACKEND-TARGET-FOLDER\app_offline.htm" -ItemType File -Force
Start-Sleep -Seconds 5
robocopy "." "BACKEND-TARGET-FOLDER" /E /XF appsettings.json appsettings.*.json app_offline.htm
Remove-Item "BACKEND-TARGET-FOLDER\app_offline.htm" -Force

# --- Frontend ---
cd ..\..\Frontend
$env:VITE_BASE_URL  = "https://THE-REAL-API-ADDRESS/api/"
$env:VITE_IMAGE_URL = "https://THE-REAL-API-ADDRESS/Image/"
$env:VITE_QR_URL    = "https://api.ecomreg.gov.mm/QR/"
npm install --legacy-peer-deps
npm run build
robocopy "dist" "FRONTEND-TARGET-FOLDER" /E /XF web.config

# --- Confirm ---
curl "https://THE-REAL-HEALTH-URL/health"
